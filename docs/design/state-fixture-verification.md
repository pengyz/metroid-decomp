# design：状态夹具验证机制（state-fixture）——设计与对抗性审查记录

> 状态：设计稿 v1（2026-10-14），经用户提出 + 对抗性自审修正，待独立复核。
> 背景问题：原版无即时存档（密码系统），能力验证（跳跃弧线/变球/门/敌人接触）若每次从
> 开机跑完整输入链，场景脆弱（G4 卡死态教训）且组合爆炸。

## 0. 用户原始思路

> 用存档把角色设置到目标状态（能力/位置），加载后验证各种能力；游戏不能随时存档就自己实现。

**裁定：方向正确**——这是 L2（纯函数快照）与 L3 全帧对拍之间缺失的**状态级行为验证**，
让「能力 × 状态」矩阵可枚举。三个陷阱需修正（下述 T1-T3）。

## 1. 事实基线

| 侧 | 随时存档 | 机制 |
|---|---|---|
| 原版游戏 | ❌ | 密码系统（进度继续），无即时存档 |
| oracle（Mesen2） | ✅ | savestates；Lua `emu.write` 内存写 |
| game-core（Rust） | ✅ | 状态构造是第一公民（重写路线红利） |

## 2. 对抗性审查：三个陷阱与修正

### T1 人造状态 ≠ 可达状态
poke 出的状态可能是真实游戏**不存在的组合**（能力标志与派生内部状态不一致），假状态上
验证的行为真实游玩未必成立。
**修正**：① 夹具值必须从**真实游戏证据**导出（真实获得能力瞬间的 RAM diff）；
② L5 流程级保留真实链路验证可达性；③ 夹具声明「基于哪次真实证据」。

### T2 same-source 的状态版
「变球能力 = 哪些 RAM 字节」目前是 C 级假设（findings/samus-movement-observations.md H2/H3）。
猜错字节 = 在无意义状态上做无意义验证。
**修正**：夹具每个地址带证据指针（A/B 级）；先走**状态发现流程**（§4）再立夹具。

### T3 二进制 savestate 的红线与跨侧不同源
savestate = 全机快照 = ROM 衍生数据（**不入库红线**），Mesen 版本绑定，Rust 侧无法消费。
**修正**：**文本状态夹具**（可入库 JSON）为唯一消费格式；savestates 降级为发现工具（留 analysis/）。

## 3. 机制设计

### 夹具格式（`oracle/fixtures/<name>.json`，文本入库）
```json
{
  "id": "fx-morph-ball-start-room",
  "description": "起始房间、已获变球、面朝右",
  "source_evidence": "真实通关取球时刻 RAM diff（A 级指针：trace id / 场景）",
  "writes": [{"addr": "0058", "value": 2, "why": "能力标志（证据指针）"}],
  "watch": ["zp", "iram"]
}
```

### 场景 DSL 扩展（工具层）
`fixture <name>` 指令 → 场景帧 0 执行夹具 writes：
- **oracle 侧**：Mesen2 Lua `emu.write`（帧 0，inputPolled 前）
- **game-core 侧**（S5）：同一 JSON 构造初始状态向量——**两侧同源起点**，帧对齐天然成立

### 验证形态
`fixture × 能力检查` 组成 L3 场景库（例：`fx-morph-ball` + 按下+跳跃 → 变球滚动轨迹
逐帧对拍；`fx-all-items` + 各武器 → 弹道/伤害状态向量）。与既有分工：

| 层 | 管什么 | 覆盖 |
|---|---|---|
| L2 | 纯逻辑函数单元 | S 面 450 格的函数级 |
| **夹具 L3** | **状态 × 能力行为**（新增） | B 面场景清单 × 状态空间 |
| L4 | 视觉等价 | 渲染 |
| L5 | 真实链路可达性 | 状态真伪 + 全流程 |

## 4. 状态发现流程（夹具值的证据来源）

```
① 真实证据获取：输入链走到能力获取点（或 savestate 辅助定位时刻）
② 前后 diff：获得能力前后 2KB RAM 帧级 diff → 候选地址集（A 级观察）
③ 消融验证：只写候选地址到「无能力」基线 → oracle 行为是否变为「有能力」
   （行为级确认因果，非仅相关）→ 晋级夹具值（B 级以上）
④ 夹具登记：source_evidence 填 ①③ 的可复现指针
```

## 5. 实施顺序（接 G4 pilot 之后，B 面铺量的关键基建）

1. `fixture` DSL + `emu.write` 落地（scenario_run / scenario_capture，含失败探针）
2. 发现流程实证第一个夹具（建议：Samus 变球能力——配合 G4 首切片）
3. 夹具 × 能力场景库模板（l3 case 扩展 fixture 字段）
4. game-core 侧夹具消费接口（S5 起点构造）

## 6. 风险登记

- 夹具值腐化（ROM 版本/场景前提变化）→ manifest sha 对锚机制延伸到夹具证据；
- 状态组合爆炸 → 夹具按能力分层（基础能力组合优先，边缘组合挂 B 面场景增长）；
- emu.write 可用性（未在已验证 API 清单）→ 首步微探针验证（同 execute 回调教训：**先证语义再用**）。
