## 1. 测法与成本

每个用例三步：派生 oracle 用例（剥 `capture*`，追加 3 条窄区间 `watch_range`）→
Mesen 采集（**串行**：Mesen 单实例）→ Rust 腿 `--state-out`（无渲染腿）→ 逐帧比对。

| 项 | 实测 |
|---|---|
| oracle 腿合计（14 案，一次性） | **437.0s** |
| rust 腿合计（14 案，cargo 已编译） | **11.8s** |
| diff（毫秒/案） | ≈0 |
| **全量重跑（oracle 缓存命中）** | **≈12s** |

对比 L4 `run-all` 的 440s：**同样覆盖 14 个用例，语义面快 36 倍**，且粒度从
112 个采集点提升到 **16300 帧 × 15 列**。

## 3. 结论

**13/14 用例、14895/16300 帧、15 列逐帧语义完全一致。唯一分叉是密码提交转场，
且是同一个已知量：从 f1189 起 `FrameCount` 恒定领先 2 帧。**

`fc` 差值分布（rust − oracle）：`0` ×1178、`+1` ×1（f1189）、`+2` ×1392、
`−254` ×12（u8 回绕，等价 +2）。其余列（`t3`/`st`/`mr`/`sy`/`sx`/`bsp`/`ia`/`hp`）
的分歧都是这个相位差的**下游派生**：`t3` 每 10 帧递减，相位差导致切换帧错位；
`st`/`mr`/`sy`/`sx` 集中在 f1190-1199 的转场邻域（十来帧内两侧都收敛到同一序列）。

逐帧结构（`fc` 与 `mr` 并读）：

| | emu | rust |
|---|---|---|
| 段一 f1189–1191 | 冻结 3 帧（`mr` 仍 0，链在跑） | f1189 正常 `inc`、f1190 链完成（`mr`=1） |
| 段二 f1193–1198 | 冻结 6 帧（`mr`=1→2） | f1191–1197 一个 span（7 帧） |
| 合计 | **9 帧逝去** | **7 帧 → 差 2** |

## 4. 未采样帧（不是分歧，必须显式区分）

`frames_only_oracle` 合计 **155 帧**，`frames_only_rust` **0 帧**——
即「oracle 有帧、Rust 无行」的单向缺口，成因是 Rust 只在主循环 spin 出口落行，
而 span（掉帧窗/长例程忙跨）期间迭代未完成、没有 spin 出口。
这是**采样面差异而非行为差异**，工具用 `FRAMES_ONLY_*` 与 `frames_only=` 显式列出，
不参与一致性计数，也不被静默丢弃。

## 5. 这份基线改变了什么

1. **「核心机制大多已实现但无证据」这句话现在有了数量答案**：非密码路径的
   状态机推进、计时、坐标、房间装载、门交互、变球、爬行、跳跃、碰撞、滚屏、
   射击杀敌——**13 个用例逐帧 15 列全同**。它们此前只有像素证据，现在有语义证据。
2. **唯一待修项被孤立出来**：密码转场的 +2 相位。它同时也是 L4 最后两格
   `f700=23px / f1100=42px` 的成因（像素栈早前已证 emu f700 ≡ rust f698、
   光标闪烁由 `FrameCount & $08` 驱动）。**一个机制修好，两套栈同时归零。**
3. **规格 §9.2 列的 7 项未实现分支（`PauseMode`/`PrepareGameOver`/`UpdateAge`/
   START 暂停开关…）没有任何用例触达** —— 与本基线 100% 全同并不矛盾，
   因为它们从未被执行。这是「绿≠完整」（AGENTS §0 D7）的又一次实证：
   **基线全同只证明走过的路对，不证明没走过的路对。** 要覆盖它们必须新增场景卡。

## 6. 为什么不顺手补那 2 帧

补 2 个 span gate 是拟合。r9 已警告过这条路的性质：忙长依赖密码字节数
（`count=0` 反而 256 次最忙）、NAR 路径跳 `Unscramble` 零忙 ⇒ 换密码就过量。
试算「CHR 字节 × 22 周期」也不成立：`LoadSamusGFX` 6000B ⇒ 4.4 帧，而 emu 实测
段一只有 3 帧 —— 忙时主体不是 `$2007` 写，而是 `DrawRoom`/`FillRoomRAM` 等指令级工作。
**要真修必须回到逐条周期会计**（本轮之前已由用户裁定冻结的全局估计器路线）。
