## 4. 丢帧账本与 f1574 门径窗（本轮重点）

取数口径与 `docs/findings/fc-drop-accounting.md` §8 完全一致：

- emu 侧：`analysis/traces/fcdoor.frames.jsonl`（1700 帧探针，watch `002d 0056 0058 001e 001a 005a`）相邻帧 `$002D` 相等 ⇒ 该帧没推进迭代；
- rust 侧：本轮 `rust/full.state.jsonl` 缺行 ⇒ 该帧迭代被吞（一行=一次迭代）。

```
emu  drops ≤f1573 = 27   rust drops ≤f1573 = 27   XOR = 0      ← 逐帧集合相同
emu  drops ≤f1700 = 28   rust 窗口起点状态与 emu 逐字节相同（见下表）
f1574 窗口：emu 丢 1572/1573/1574（3 帧） vs rust 丢 1572/1573（2 帧）
```

### 4.1 为什么 #121 没改变它（A 级代码证据）

`crates/game-core/src/world/room_load.rs:234` 的 `room_load_gate_step`：

- `phase == 1` 分支：冻结窗结束 → 置 `phase=2`、`tail=0`、`RoomNumber←0xF0`，返回 `true`；
- `phase == 2` 分支：只有 `room_number()==0xFF` 的收尾判断，其余路径**只返回 `true`**；
- 该文件 **全文没有读 `$0056`（DoorEntryStatus）**——`grep -n "\\b56\\b" crates/game-core/src/world/room_load.rs` 无命中。

也就是说，代码注释里写的「门入场时 `room_load_tail==2 && $56 != 0` 多补一格尾段」**只有注释、没有实现**；#121 把 `advance_room_load_tail` 改成「一次调用推一格」（对齐 `AttribTableWrite ; 07:EA13`），但**没有新增门径的那一次补推**，所以门径窗口长度不变。

## 6. 下一条建议（只给一条，不扩范围）

**卡：门径载房窗补一次 `AttribTableWrite`（`world/room_load.rs`）**

- 改动点：`room_load_gate_step` 的 `phase == 2` 分支，在「`tail==2 && DoorEntryStatus($0056)!=0`」时补调一次 `crate::world::room_draw::attrib_table_write(mem)`（即 `advance_room_load_tail` 的一次推进），其余路径不动。
- 验收（三条，全部机械可判）：
  1. `f1574` 窗口长度：rust 变为丢 1572/1573/1574 三帧（与 emu 同集合）；用 `fcdoor.frames.jsonl` 与新跑 rust 腿复算，XOR(≤f1574)=0；
  2. `≤f1573` 的 27/27 XOR=0 **保持**（不得为凑窗口而改动开机段）；
  3. **首分歧仍应是 f1301 `$0454` 2 字节**——若它提前或后移，说明补推影响了内容面，必须停下来重新定界，不能把它当成功。
- 不改任何覆盖率/容差判据；L4 `run-all` 维持 ≥171/172。
