## 0. 结论

1. **能回代的规则只有一条，而且它是定义换写的、不是成本模型**：边界帧 f 上「`$2007` 写次数 = 0 且 `FC(f) == FC(f−1)`」⇔ 超；「写 30 次且 `FC(f) = FC(f−1)+1`」⇔ 便宜。对窗口内 **31/31** 个边界帧成立（目标区间 20/20）。两条判据其实是同一件事：`FC` 不前进 ⇔ 该帧没跑完一个完整迭代（收尾落到下一帧）。
2. **机制级规则在本数据面上不成立**：7 路 PC 计数向量、6 槽 × 16 B `EnsExtra`、`$2007` 写地址/字节数、名册与类型，**都出现「特征相同、判定相反」的碰撞**（§3.2–§3.4）。因此「为什么这 14 帧超、另 6 帧不超」在本卡数据里**无法定界**，只能给出最小补采清单（§4）。
3. 一条新 A 级结构事实：**超预算时流送不在边界帧完成**——该帧 `$2007` 写 0 次、`$F345` 零命中；列写顺延到下一帧（f+1，`X` 不变、`FC` 才 +1）。便宜帧则在边界帧内完成「进列 + 30 字节写」。

## 2. 判别规则

### 2.1 R1（观测级，**成立 31/31**）

> 在边界帧 f：若 `$2007` 写次数 = 0 **且** `FC(f) == FC(f−1)` ⇒ 该帧超、`ScrollX` 下一帧不推进；
> 若 写 > 0 **且** `FC(f) = FC(f−1)+1` ⇒ 便宜。

回代：目标 20 帧全部命中（14 超：写 0 且 FC 同前帧；6 便宜：写 30 且 FC+1）；扩展到 `X=8…88` 的 11 帧也全命中 ⇒ 31/31。
其中 `f1606`（`X=8`，窗口首个边界帧）`$2007` 写 **62** 次——整屏初绘；因此便宜一侧的判据写「写 > 0」而不是「写 = 30」，否则该帧会被误判。目标区间 20 帧的便宜侧确实都是 30。

```bash
python3 - <<'EOF'
import json
from collections import Counter
rows=[json.loads(l) for l in open('analysis/traces/kraid29-sweep.frames.jsonl')]
x={r['f']:r['w']['ScrollX'] for r in rows}; fc={r['f']:r['w']['FC'] for r in rows}
p='analysis/_probe/v2pc/_tmp_sweep_1629615-1795445195_a2_r29.ntwrites.jsonl'
wr=Counter(json.loads(l)['f'] for l in open(p) if l.startswith('{"f"'))
prev=None;b=[]
for r in rows:
    v=r['w']['ScrollX']
    if prev is not None and v>prev and v%8==0: b.append(r['f'])
    prev=v
ok=0
for f in b:
    lab='超' if x[f+1]==x[f] else '便宜'
    rule='超' if (wr.get(f,0)==0 and fc[f]==fc[f-1]) else '便宜'
    ok += lab==rule
print('R1 matches', ok, '/', len(b))
EOF
# 期望：R1 matches 31 / 31
```

**R1 的性质**：它的两条其实是**同一个定义的两种写法**——`FC` 不前进 ⇔ 该帧没跑完一个完整迭代 ⇔ 迭代的收尾（含列流送）落到下一帧。所以「31/31」不是独立预测能力的证据，只是确认两个观测量（`$2007` 写次数、`FC` 是否前进）与定义自洽；它**没有解释**谁吃掉了预算。**不得把它当成本模型**；V2 实现不得用 R1 反推成本，否则等于用结果当原因。

### 2.2 R2（7 路 PC 计数向量）——**无效，有反例**

要点：**超帧 f 本身零命中**（`$F345` 不执行），它的敌人更新发生在**前一帧 f−1**；所以要比的是「超帧的 f−1」与「便宜帧的 f」——两边都是「一次完整敌人环迭代」的计数。

| 执行迭代所在帧 | pc-vec（`$F345,$F351,$F37F,$F3BE,$F3E6,$F410,$E094`） | 该次迭代之后的边界帧 | 判定 |
|---|---|---|---|
| f−1 = 1657,1662,1667,1672,1677 | `1,6,6,6,0,0,6` | 1658,1663,1668,1673,1678（该帧本体全零） | 超 |
| f = 1683,1687 | `1,6,6,6,0,0,6` | 1683,1687 | 便宜 |
| f−1 = 1690,1699,1704,…,1734 | `1,6,6,5,1,1,6` | 1691,1700,1705,…,1735（本体全零） | 超 |
| f = 1696,1740 | `1,6,6,5,1,1,6` | 1696,1740 | 便宜 |

⇒ **同样的七路计数，既产出超也产出便宜**（`1,6,6,6,0,0,6`：5 超 vs 2 便宜；`1,6,6,5,1,1,6`：9 超 vs 2 便宜）。真正要问的是「为什么这一帧没进敌人环 / 为什么这一次迭代没在帧内收尾」，而七路计数到不了「分支走了不同的路」这一层；要判别必须**按槽记录进入的例程与分支目标**（§4.1）。

### 2.3 R3（6 槽 × 16 B `EnsExtra` 末态）——**无效，已否证**

分母要写清（两种口径都能复现）：
- **目标 20 帧**：只有 **15 个不同向量**，其中 **3 个同时带两种判定**；
- **窗口 31 帧**：**16 个不同向量**（`X=8…88` 那 11 帧多出 1 个向量）。

三个混合向量及其帧对（目标 20 帧内）：
- `mixed#1`：1663（超） vs 1683（便宜）；
- `mixed#2`：1668（超） vs 1687（便宜）；
- `mixed#3`：1715（超） vs 1740（便宜）。

这与 #30 的冲突组同源，再次确认：**末态字段不可分**，不得再用它做成本模型输入。

### 2.4 R4（流送量/地址）——**否定**

**超帧的顺延写帧（f+1）** 与 **便宜帧的本帧（f）** 都是 **30 次 `$2007`**，地址形状相同（`$2C00+col …`，如便宜帧 1650 写在 `1650` 的 `2C0C..`、超帧 1658 的列写出现在 `1659` 的 `2C0E..`），值分布也相同（4 个非 `FF` 后接 `FF`）。
反之：便宜帧的 `f+1` 写 0 次（已在 f 写完），超帧的 f 写 0 次——这正是「顺延」的含义。⇒ 每次列流送的写次数与地址不随判定变化，变量不在流送本身。

### 2.5 R5（名册/类型）——**无效**

6 槽名册恒为 `[8,9,9,9,10,10]`（类型 8=Metroid、9/10=两种 hopper），`status` 只在 `1691` 起 slot0 由 1 变 2；与 14/6 划分无对应。

### 2.6 R6（迭代周期）——**不能当工作量**

`cycles.tsv` 是 `$F345` 入口的 `cpu.cycleCount`。跨帧差 ≈ 29780/帧；超帧的迭代跨 2 帧 ⇒ 差值 ≈ 2×29780。这是「跨了几个 VBlank」的另一种写法，**不是**工作量（工作量要在迭代结束处取，本数据没有该采样点）。

## 3. 结构事实（A 级，可独立引用）

1. 超预算帧上 `$F345` 零命中 ⇒ **该帧没有敌人环迭代**（敌人环只在迭代的第一显示帧执行）；名册与状态在该帧保持不变。
2. 超预算的列流送**顺延一帧**：`f` 帧 X 已到目标列但写 0 次，`f+1` 帧写 30 次而 X 不动；便宜帧在 `f` 内同时完成进列与 30 写。
3. 迭代周期与 `FC`：`FC` 在超帧与前一帧相同，只在顺延帧 +1（与 `MainLoop` 每迭代 `inc FrameCount` 一致，见 `docs/spec/timing-primitives.md` §2）。

## 4. 下一步要采什么（最小清单）

要回答「14 超 / 6 便宜」，必须补三样里至少两样；现在的数据都不够：

1. **按槽的例程入口**（这才能到 §2.2 说不到的「分支走了不同的路」）：
   - 在 `$F351`（敌人环入口）记录 `(frame, slot, $F351)`，每个 slot 单独一行；
   - 在 `$F3BE/$F3E6/$F410` 记**分支目标**（`emu.getState()["cpu.pc"]` 或 hook 前的 `pc`），不只计数；
   - 窗口 1600–1760，19/20 个边界帧 + 各自前一帧。
2. **迭代工作量采样点**：在 `MainLoop` 的 `lda #$00 / sta NMIStatus`（工作结束）与等待出口各记一次 `cpu.cycleCount`，得到「单迭代净工作周期」；现在的 `$F345` 采样只能得到跨帧量。
3. **按槽屏上位置**：本 trace 只有 `EnsExtra`，**没有 `Ens`**（`y/x` 与页字节），所以连「几个精灵在屏上、是否压在同一扫描线」都算不出；要在 sweep 采集里加 `watch_range0400-04FF` 才能拿到 `Ens` 全量（224 B+224 B）。

附加建议（不是必须）：若 1–3 仍不可分，再挂 `$2005/$2006` 写时间戳（相机寄存器写在与敌人环谁先谁后）与 PPU 精灵溢出计数（8 sprites/scanline 的 CPU 停顿是 NES 上真实的、随精灵布局变化的开销）。

## 5. 假设区（B/C 级，不得进结论）

- **H1（B）**：14/6 的划分由「该列对应的敌人更新工作量」决定，而工作量随敌人**状态机内部相位**变化——但状态向量已被 §2.3 否证，故需按槽分支目标才能验证。
- **H2（B）**：PPU 精灵溢出（同一扫描线 >8 精灵导致 CPU 停顿）可能吃掉了预算；本数据缺 `Ens` 位置，**无法验证**。
- **H3（C）**：14/6 与列号（`col 14–18,21,23–30` 超；`1–13,19,20,22,31` 便宜）有相关，但列号是「相机走到哪」的代理量，不能当原因；且 `col=22` 便宜而 `21/23` 超，单调性不成立。
